# How it works

This page follows a test session from the first `lakeflow.job()` call to the last cleanup, and says what the plugin leaves in the workspace.

## Session setup

Creating a `Lakeflow` does nothing. The first time a test asks it for a job template, the plugin sets up the bundle target. Setup is keyed on the bundle root, target, profile, variables, sync strategy, helpers path and deploy flags, and happens once per key per session, however many `Lakeflow` instances share it.

1. **CLI check.** `databricks --version` must report v1.7.0 or later.
2. **Templates.** With `sync="deploy"`, the plugin runs `databricks bundle deploy -t <target> --auto-approve`, followed by any `deploy_flags`, then `databricks bundle summary -t <target> -o json` for the deployed job ids, then `jobs.get` for each id in parallel. Every `bundle` command gets `--var name=value` for each of `Lakeflow`'s `variables`, sorted by name. Before `jobs.get`, the `workspace.host` from the summary is compared with the workspace client's host, ignoring scheme, trailing slash and case, and a mismatch fails setup with a `LakeflowError` that names both hosts, instead of every `jobs.get` failing with `NotFound` and the jobs looking stale. The deployed settings are the templates, with workspace paths for notebooks and uploaded wheels. A job that the summary lists without an id is recorded as not deployed, and a job whose id no longer exists in the workspace as stale, so that using it fails with a clear message instead of a bare API error. With `sync="sync"` or `"none"`, the templates come from `databricks bundle validate -o json` instead, after a `bundle sync` for `sync`, and the host check reads `workspace.host` from the validate output. See [sync strategies](configuration.md#sync-strategies) for what those refuse. From the same summary or validate output, the plugin lists the `artifacts` that build wheels (`type: whl`, or a `build` command and no `type`) without `dynamic_version: true`. Serverless caches wheels by file name, so the first template lookup warns about them once per session and xdist worker, or raises `LakeflowError` with `strict_artifacts=True`, see [Limitations](limitations.md).
3. **Helper notebooks.** Two small Python notebooks, one that sets task values from a widget and one that reads them and returns them as JSON, are uploaded to `helpers_path` with overwrite. Their widget names start with `__pytest_` because every job parameter is pushed into every notebook task's widgets.
4. **Sweep.** With `--lakeflow-sweep`, the first process to finish a setup sweeps, once for the session: under xdist the workers share the sweep through a file in the shared directory, as they share setup. It lists your jobs, or everyone's with `--lakeflow-sweep-scope=all`, and deletes those tagged `pytest` whose `pytest_run_id` differs from this run and whose creation time is older than `sweep_hours`, or whose `pytest_expires` time has passed. `--lakeflow-sweep-branch` narrows that to one `pytest_git_branch`. `--lakeflow-sweep-schemas=<catalog>` also drops old `pytest_<run id>_<hex>` schemas of other runs, and `--lakeflow-sweep-notebooks` old `setup_<hash>` and `teardown_<hash>` notebooks from the helpers folder of that setup. `--lakeflow-sweep-dry-run` only lists them, and `--lakeflow-sweep-report` writes them to a JSON file. See [sweeping leftovers](configuration.md#sweeping-leftovers).

The result, job templates as dicts, template errors, helper paths and the unversioned wheel artifacts, is JSON. If setup fails, the error is remembered and every later use in the session fails with the same message instead of retrying the deploy.

### Parallel sessions

Under pytest-xdist, the controller creates a temporary directory and passes it and the run id to every worker. The first worker to need a bundle target takes a `FileLock` on a state file named after the bundle key, runs the setup and writes the JSON. Workers that arrive later read the file. A setup error is written too, so all workers report it. Each worker builds its own `WorkspaceClient`, and the controller deletes the directory at the end.

## Isolating test deployments

Every session that deploys the same target deploys into the same `workspace.root_path`. When a second session, a developer and CI, or two CI pipelines deploy that target while the first session's jobs are running, the deploy replaces the wheels under `artifact_path/.internal/` and the running copies fail when they look for the old ones. The plugin cannot tell sessions apart inside one target, because it reads its templates from whatever the target holds. Give each identity and branch its own deployment in `databricks.yml` instead:

```yaml
variables:
  lakeflow_suffix:
    description: Keeps one test deployment per branch apart from the others.
    default: local

experimental:
  skip_artifact_cleanup: true

targets:
  test:
    mode: development
    workspace:
      root_path: ~/.bundle/${bundle.name}/test/${var.lakeflow_suffix}
```

`~` is the home folder of the identity that deploys, so a developer and a CI service principal never share a deployment. `${var.lakeflow_suffix}` separates branches. `experimental.skip_artifact_cleanup` stops a deploy from deleting the wheels that the previous deploy of the same root uploaded, so a redeploy from the same branch does not break jobs that are still running.

Pass the variable from the `lakeflow` fixture in the root `conftest.py`. `Lakeflow`'s `variables` go to every `bundle` command as `--var name=value`, `bundle destroy` included, and are part of the setup key. Under pytest-xdist each worker hands the root, target, profile and variables it deployed to the controller, so `--lakeflow-destroy` destroys the same deployment. Branch names can contain `/`, so replace anything outside letters, digits, `_` and `-`:

```python
import os
import re

import pytest

from pytest_databricks_lakeflow import Lakeflow


@pytest.fixture(scope="session")
def lakeflow() -> Lakeflow:
    return Lakeflow(
        variables={"lakeflow_suffix": re.sub(r"[^A-Za-z0-9_-]", "-", os.environ.get("GITHUB_HEAD_REF") or "local")},
        deploy_flags=["--fail-on-active-runs"],
    )
```

Each branch then leaves its own deployment behind, so end the pipeline with `pytest --lakeflow-destroy`, which runs `databricks bundle destroy` for the targets the session deployed.

The `deploy_flags` argument passes `--fail-on-active-runs` to `bundle deploy`, which then refuses to deploy while a job that the bundle deploys has an active run. It catches someone running the deployed test target's jobs by hand. It does not catch a concurrent test session, because the plugin never runs the deployed jobs: every test runs a separate `[pytest]` copy, and the CLI does not look at those. Only separate deployments protect one session from another.

## One ephemeral job

### Build the settings

1. `lakeflow.job(key)` or `lakeflow.task("key.task")` deep-copies the template into a fresh `JobSettings`. With `task_params`, `check_task_params` warns about each name that is also a job parameter and `apply_task_params` merges a mapping into a task's named parameters or replaces its positional ones with a list, before any helper task exists, so stubs and probes are never targets; a task test may name only its own task. For a job test, `disable_tasks` sets `disabled` on the tasks named in `disable`, raising `LakeflowError` with the available task keys for an unknown one. `force_conditions` then replaces each named condition task's operands with `true == true` or `true == false`, logging the original ones at INFO, and raises `LakeflowError` for a task that is not a condition task or is disabled, before changing anything. With `extra_dependencies`, `add_dependencies` appends each one to every environment of the copy and, as a `pypi` or `whl` library, to every notebook, Python script and Python wheel task on a cluster, raising `LakeflowError` for a local path. This happens before the helper tasks and environment are added, so they never install them.
2. For a job test, `override_tasks` first sets the fields in `task_overrides` (`timeout_seconds`, `max_retries`, `min_retry_interval_millis` and `retry_on_timeout`) on the named tasks, raising `LakeflowError` before changing anything for a task key the template does not have, naming the available tasks, or another field, naming the four. It runs before any helper task is added, so stub, probe, setup and teardown keys are unknown to it. `inject_probes` then appends a probe task for each entry in `capture_task_values`. For a task test, `task_overrides` may name only the target task, else `LakeflowError` is raised; `wrap_task` keeps only the target task, gives it a stub task for each entry in `upstream_task_values` as its only dependencies, and appends a probe if `capture_task_values` is set, and `override_tasks` then applies `task_overrides` to the target. Helper tasks get the `__pytest_serverless` environment, or the `helpers_compute` job cluster. A job allows at most 10 environments, so `LakeflowError` names the template's environments when it already has 10 and the helper environment does not fit.
   With `setup=` or `teardown=`, `inject_lifecycle` then adds the `__pytest_setup` task first, making every task without `depends_on`, stubs included, depend on it, and the `__pytest_teardown` task last, depending on every task that nothing else depends on, probes included, with `run_if` `ALL_DONE`. Both are notebook tasks on the helper compute, with a `__pytest_params` widget that names the job's declared parameters. Their notebooks hold the function's source and a call that passes the arguments it declares, and are uploaded to `helpers_path` as `setup_<hash>` and `teardown_<hash>`, where the hash is the first 12 hex digits of the notebook's SHA-256, once per distinct notebook per session. The function is checked before anything else, so a lambda, a function without readable source, a closure, an unknown parameter or a decorated function raises `LakeflowError` before the template is read. The notebook starts with `from __future__ import annotations`, so the function's annotations are never evaluated on the cluster.
3. `sanitise` strips what would make the copy run on its own, notify people or count as bundle-managed: `deployment`, `edit_mode`, `schedule`, `trigger`, `triggers`, `continuous`, `email_notifications`, `webhook_notifications`, `notification_settings` and `parent_path` on the job, and the notification fields on every task. Unless `side_effects="keep"` is passed to `Lakeflow`, it pauses dashboard and SQL alert subscriptions: `dashboard_task.subscription.paused` is set on every dashboard task with a subscription and `sql_task.alert.pause_subscriptions` on every SQL alert task, leaving the subscribers and the rest of the task as they were. Alert tasks and Power BI tasks are left as they are in both modes. It strips `run_as` too, unless the test passed `run_as`: `"keep"` keeps the template's, and a principal replaces it. It sets `disable_auto_optimization` on serverless code tasks (notebook, Python script, Python wheel and JAR tasks with no cluster or warehouse) unless told otherwise. It applies the compute overrides that are set: `environment_version` replaces the environment version of every environment except `__pytest_serverless` and those whose spec sets `base_environment`; `budget_policy_id` sets the job's budget policy; `existing_cluster_id` moves every task that has a `job_cluster_key` or a `new_cluster`, helper tasks and tasks nested in a `for_each_task` included, onto that cluster, drops `job_clusters` and leaves serverless and warehouse tasks alone; `single_node` then makes every remaining job cluster and task `new_cluster` a single node cluster (no workers, no autoscaling, the single node `spark_conf` and `ResourceClass` tag merged over the cluster's own), raising `LakeflowError` for a cluster in standard access mode. It then overrides the performance target if `performance_optimized` is set, allows one concurrent run, sets the job's `timeout_seconds` to `Lakeflow`'s `timeout` plus 60 seconds unless the template already has a smaller positive one, names the job `[pytest] <test node id>` within the 4096-byte limit, and adds the tags `pytest`, `pytest_run_id` and `pytest_nodeid` to the template's tags within the 25-tag limit, raising `LakeflowError` when they do not fit. It then adds the attribution tags that could be resolved, in this order and only while the job has fewer than 25 tags: `pytest_ci_url` (the GitHub Actions or Azure DevOps run page), `pytest_user` (`GITHUB_ACTOR`, then `BUILD_REQUESTEDFOREMAIL`, then the workspace user), `pytest_git_sha` and `pytest_git_branch` (from the CI variables, then `git` in the rootdir; a detached HEAD gives no branch tag). Tag values are made Latin-1, one line and at most 256 bytes. The job description becomes the test node id and the CI run URL, followed by a blank line and the template's description when it has one. With `test_marker=True`, `inject_test_marker` then declares the job parameter `__pytest_test_id` with the test node id as its default, trimmed to 4096 bytes, replacing a template definition of the same name. It carries the node id even when `name` replaces it in the job name. The `pytest_nodeid` tag carries the node id too, but only the parameter is visible to job code.
   With `environments`, `merge_environments` then merges each override into the copy's environments: a field replaces the template's field, so a per-job `environment_version` wins over the session-wide one and `dependencies` replaces the list `extra_dependencies` extended, and a new key is appended. It raises `LakeflowError` before changing anything for a key starting with `__pytest_`, a field that `compute.Environment` does not have (`from_dict` would drop it silently), a spec with both `environment_version` and `base_environment`, or more than 10 environments, naming every key.
4. A `performance_target` of `STANDARD` in the template triggers a warning, because it adds 3 to 4 minutes to every run.
   Each Run Job task that is still in the copy and not disabled, nested `for_each_task` tasks included unless their loop is disabled, triggers a warning, because `sanitise` keeps its `run_job_task` as deployed: the copy runs the deployed child job, not a copy of it. With `children="refuse"` the plugin raises `LakeflowError` here instead, so nothing is created.
5. A finaliser is registered on the test so the job is closed at teardown if no `with` block closes it first.

### Create and run

1. Entering the `with` block, or the first `run()` or `start()`, calls `modify_settings` if set, checks that `params` are declared, checks that every Python script, Python wheel, JAR and dbt task has a cluster or an `environment_key` (serverless requires one, so `LakeflowError` names the tasks without), and calls `jobs.create` with the settings fields that `create` accepts and `access_control_list` from `permissions`, which is `None` when there are none. Errors from `jobs.create`, such as `PermissionDenied` for a `run_as` you may not use, fail the test unchanged. The job URL is logged and recorded in the test's `user_properties`.
2. When `run()` or `start()` is given a `timeout` that, plus 60 seconds, is longer than the job's `timeout_seconds`, it first calls `jobs.update` with that value as `timeout_seconds` and the copy's `tasks`, and remembers the new value, so a later run with the same timeout makes no second update. The tasks are sent because `jobs/update` reads a body without `tasks` on a one-task job in the legacy single-task format, where `timeout_seconds` lands on the task and the job's own is unchanged. The change is logged at INFO, or at WARNING when the shorter value came from the template or `modify_settings` rather than from `Lakeflow`'s `timeout`. `RunHandle.wait()` cannot do this, because its run has already started, so it raises `LakeflowError` when its `timeout` is longer than the job's `timeout_seconds`, naming both, `run(timeout=...)` and `start(timeout=...)`; the `timeout` given to `start()` becomes the default of `wait()`, so `run()` is `start(timeout=...)` followed by `wait()`. `run()` raises `LakeflowError` before anything else when `stop_after` is longer than its `timeout`; `wait()` does so when it is called, against its own timeout, and the run goes on. `run()` and `start()` raise `LakeflowError` before starting the run when the test passed `full_refresh`, `full_refresh_selection` or `refresh_selection` but the job has no pipeline task, nested `for_each_task` tasks included, naming the job's tasks. Otherwise they merge the run's parameters over the job's, extend `only` with the stubs and probes the selected tasks need and with the setup and teardown tasks, and call `run_now` with `job_parameters`, `only`, a fresh idempotency token, `performance_target` and `queue` when the test passed them, and `pipeline_params` when the test passed `full_refresh`, `full_refresh_selection` or `refresh_selection`. A retried request with the same token returns the run it already started instead of starting another. The run is added to the job's active runs, and one `get_run` records its URL in the test's `user_properties`, so a run that is never waited for still appears in the report. `start()` returns a `RunHandle` here; `run()` goes on to wait, as `RunHandle.wait()` does.
3. Waiting polls `get_run` until the run terminates, rather than using the SDK waiter, which raises on an ordinary task failure. It sleeps `Lakeflow`'s `poll_interval` between polls, two seconds by default, and starts from the poll that started the run. Each poll compares every task run's state with the previous poll and logs a line at INFO for each change, such as `transform: RUNNING -> FAILED in 0:00:42 ValueError: no rows`, and adds it to the test's `lakeflow` report section. The state is the V2 `status.state` while the task runs and the result state once it has terminated, falling back to the legacy life cycle state when the run has no V2 status. The output of each task run that terminated since the previous poll is read with `get_run_output` straight away, which gives the line its error, and kept for building the `JobRun`, so each output is read only once. When the timeout expires the run is cancelled and `LakeflowTimeout` is raised; its message ends with a `Tasks when cancelled:` line giving each task run's state at the last poll, such as `extract SUCCESS, transform RUNNING, load PENDING`. With `--lakeflow-report-dir`, before raising, the plugin polls the cancelled run until it has ended, for at most 60 seconds, builds its `JobRun` and adds it to the test's `report.json`, without appending it to `job.runs` or calling `run_finished`; leaving the job with a run still active does the same for that run. The job's `timeout_seconds` is 60 seconds longer, so this client-side cancel normally wins and the platform's timeout is the backstop for a test process that died. A run the platform stops ends `TIMEDOUT` and is returned as a `JobRun` like any other. With `stop_after`, once that long has passed since the run started, the plugin calls `cancel_run` once and goes on polling, keeping the run among the job's active runs until it has terminated; the run then ends `CANCELED` and is returned as a `JobRun` whose `cancelled` is true. The `timeout` still applies after the cancel, and raises `LakeflowTimeout` without a second `cancel_run`.
4. Building the `JobRun` keeps every attempt of each task, calls `get_run_output`, in parallel, for each attempt that ran and whose output was not already read while polling, parses errors from the `error` field (falling back to the last `Name: message` line of the trace), parses each probe's JSON output into the `values` of the task it watched, reads each condition task's `outcome` into `condition_outcome`, sorts tasks into `tasks`, `injected_tasks`, `skipped_tasks` and `disabled_tasks`, putting a `DISABLED` task in `disabled_tasks` when it is disabled in the copy's settings and in `skipped_tasks` otherwise (the run itself does not say whether a `DISABLED` task was disabled or left out by `only`), and fills in resolved parameters: `JobRun.parameters` from the run's job parameters, leaving out the plugin's own, and each `TaskRun.parameters` by calling `get_run` with `include_resolved_values=True` on each task run that ran, in parallel, because the Jobs API fills `resolved_values` only on a task run fetched by its own id and never on the job run. For each SQL file task run that ran it also reads `runs/get-output` as raw JSON, in parallel, and fills `TaskRun.sql_result` from `sql_output.file_output.query_result`, which databricks-sdk does not model. Each `TaskRun` describes the task's last attempt, and its `attempts` list holds one `TaskRun` per attempt in order. Last, it calls `jobs.export_run` with `views_to_export=CODE`, in parallel, on the last attempt of each user notebook task that `notebook_export` selects (by default those that ran and did not succeed; `"always"` every one that ran, `"never"` none), and parses the notebook view into `TaskRun.notebook`. The export works only on a notebook task run, so other task types are never exported, and neither are the plugin's stubs, probes, setup and teardown tasks. A failed export logs a warning and leaves `notebook` as `None`.
5. A teardown task that did not succeed is logged at WARNING with its error and run page. It does not change `JobRun.succeeded`.
6. `run_finished` is called if set. `RunHandle.wait()` keeps the `JobRun` and returns it again on a later call, without calling `run_finished` a second time.

### Tear down

1. Leaving the `with` block cancels any run of this job that is still active, then deletes the job unless a keep rule applies. The rules, in order: `--lakeflow-keep` or `keep=True` keeps everything; `--lakeflow-keep-failed` and `--no-lakeflow-keep-failed` override `keep_failed`; otherwise a job is kept when the block raised anything other than `pytest.skip` or `pytest.xfail` and `keep_failed` is on. Kept jobs are logged at WARNING with every run URL, and collected for the terminal summary.
2. Without `with`, the finaliser applies the same rules, treating the test as failed if its setup, call or teardown report failed.
3. `lakeflow.schema()` drops its schema with `force=True` in a `finally` block, unless `keep` or `--lakeflow-keep` is set. A kept schema is logged at WARNING and collected for the terminal summary.

## Session end

1. Every process cancels the runs it started that are still active, and counts them.
2. xdist workers report the bundle targets they deployed, the jobs and schemas they kept and the number of runs they cancelled to the controller.
3. With `--lakeflow-destroy`, the controller, or the single process, runs `databricks bundle destroy -t <target> --auto-approve` for each target deployed with `sync="deploy"`, with the same `--var` arguments as its deploy. A failed destroy is printed with the summary and turns a passing session into a failed one.
4. The controller, or the single process, prints a `lakeflow` block in the terminal summary with the kept jobs and schemas and the cancelled runs, when there are any. See [logging and reports](configuration.md#logging-and-reports).

## What is left in the workspace

- The deployed test target, unless you pass `--lakeflow-destroy`. It is only a template source, and leaving it makes the next session's deploy fast.
- The two helper notebooks under `helpers_path`, and the `setup_<hash>` and `teardown_<hash>` notebooks of any `setup=` and `teardown=` functions. Each edit of a function, and each plugin upgrade that changes the notebook around it, uploads a new one. `--lakeflow-sweep --lakeflow-sweep-notebooks` deletes those not uploaded for `sweep_hours`.
- Jobs kept by the keep rules. Their runs stay with them. `--lakeflow-sweep` deletes them once they are older than `sweep_hours`, or with `--lakeflow-keep-ttl` once their `pytest_expires` time has passed. Their `pytest_run_id`, `pytest_nodeid`, `pytest_ci_url`, `pytest_user`, `pytest_git_sha` and `pytest_git_branch` tags say where each one came from.
- Schemas kept by `keep` or `--lakeflow-keep`. `--lakeflow-sweep --lakeflow-sweep-schemas=<catalog>` drops them once they are older than `sweep_hours`.
- Nothing else. Deleting an ephemeral job removes its runs.

## Timing

Measured in one Azure workspace:

- A trivial serverless notebook test takes about 20 to 35 seconds end to end, of which about 2 seconds is API overhead.
- A probe or stub task adds 7 to 30 seconds.
- A job with `performance_target: STANDARD` adds 3 to 4 minutes to every run.
- A classic job cluster takes 2 to 10 minutes to start.
- Five jobs run at once took no longer than one.

To measure your own workspace, read `run.task(key).timing`, which splits each task's time into queue, setup, execution and cleanup. `run.effective_performance_target` shows which performance mode the run used.
