# Limitations and FAQ

## Limitations

- **Logs.** `TaskRun.logs` is only filled for Python script, wheel and JAR tasks, and holds only the last 5 MB. Notebook tasks have no logs; what a notebook printed is in `task.notebook.stdout`, read from the notebook that `jobs.export_run` renders, by default only for notebook tasks that ran and did not succeed, and only for the last attempt of a retried task: the earlier ones in `task.attempts` have `notebook` `None`. That export format is not documented, so it is parsed best effort: when it cannot be read, `task.notebook.cells` is empty, `task.notebook.html` keeps the export and a `UserWarning` is emitted, once per test that exports such a notebook. The shape of printed Python output was checked on serverless compute and on classic job clusters running 17.3 LTS and 13.3 LTS, which all export it as a standard output stream apart from standard error; Scala, R and `%sh` cells were not checked. Notebook output keeps only the first 5 MB. A truncated output or log raises a `UserWarning` naming the task, and `output_json` refuses truncated output with a `ValueError`. Databricks documents that on serverless compute the logs of one task can include output from other tasks in the same run. In our tests each task's logs held only its own output, but this is not guaranteed.
- **Cancelled tasks have no output.** A task that ended `CANCELED`, such as the tasks of a run stopped by [`stop_after`](job-tests.md#stop-a-run-that-does-not-end), counts as not run: the plugin reads no `output`, `logs`, `error` or exported notebook for it, so a cancelled notebook task has none of them. Assert on the data the job wrote instead.
- **Resolved task parameters cost one request per task.** The Jobs API fills a task's `resolved_values` only when the task run is fetched by its own run id with `include_resolved_values=true`; on the job run the field is always null. So building a `JobRun` calls `runs/get` once per task run that ran, in parallel, on top of `runs/get-output`. A task run that cannot be read leaves `TaskRun.parameters` as `None` with a warning in the log.
- **SQL rows come from SQL file tasks only.** `TaskRun.sql_result` is read from `sql_output.file_output`, a field of `runs/get-output` that the Jobs API reference does not document and databricks-sdk does not model, so the plugin reads the raw response: one extra request per SQL file task that ran. Saved query, alert and dashboard tasks give `None`; query a table the job wrote instead. A saved query task reports no rows even when it succeeds: on a successful run in the maintainers' test workspace in October 2026, its `sql_output.query_output` held only `query_text`, `warehouse_id`, `endpoint_id` and `output_link`, a link to the result page in the Databricks UI, and no `query_result`. Values are strings as the platform reports them, a NULL is `None`, and the platform keeps at most 1,000 rows (`truncated` says when it cut them) for 7 days.
- **dbt artefacts are a link that expires.** `TaskRun.dbt_output.artifacts_link` is a pre-signed URL to a tarball of the dbt artefacts, which the platform signs for 30 minutes. With `Lakeflow(dbt_artifacts=True)` the plugin downloads it while building the run, so `TaskRun.dbt` is only filled for runs that `run()` or `wait()` built, and a tarball over 50 MB is not downloaded: `dbt` is then `None`, with a warning naming the task. `run_results.json` describes the last command of the task that wrote one. See [dbt tasks](task-tests.md#dbt-tasks). report.json keeps the link and leaves out the headers.
- **`dbt_commands` needs a job without job parameters.** `job.run(dbt_commands=...)` sends a legacy run parameter, which the Jobs API refuses on a job that has job parameters, so the plugin raises `LakeflowError` first. `test_marker`, `trigger=` and `input=` declare job parameters. Use `task_params` on `job()` or `task()`, which sets the commands in the copy. The platform also resolves a dbt task's own commands in such a run, so `TaskRun.parameters` takes the run's `dbt_commands` from its `overriding_parameters` instead.
- **Alert tasks succeed whether or not the alert triggered.** Databricks marks an alert task succeeded when the alert was evaluated, so `succeeded` says nothing about the alert. Assert on `TaskRun.alert_state`. Only an alert that cannot be evaluated, such as one whose query fails, fails the task, with `alert_state` `ERROR`. The Jobs API reports no error for it, so `TaskRun.error` holds the task's termination message.
- **Alert tasks and Power BI tasks run as the template has them.** An alert task notifies its subscribers, or the alert's own subscribers when the task sets none, and the task has no pause flag, so the copy cannot silence it without disabling it. A Power BI task updates the semantic model whether or not `refresh_after_update` is set; the flag only adds an Import-mode data refresh. Disable such a task in a test with `disable=`, for example `lakeflow.job("reporting", disable=["check", "refresh_powerbi"])`.
- **Pipeline tasks run the deployed pipeline unless you copy it.** By default an ephemeral job copies the job, not the pipelines its pipeline tasks point at, so every test updates the same pipeline and its tables. Pass `pipelines="copy"` and `schema=` to `lakeflow.job()` or `lakeflow.task()` to point each pipeline task at a copy that publishes to a temporary schema, or copy one pipeline with `lakeflow.pipeline()`, see [Pipelines](job-tests.md#pipelines). `full_refresh`, `full_refresh_selection`, `refresh_selection`, `refresh_flow_selection` and `reset_checkpoint_selection` on `job.run()` apply to every pipeline task in the run.
- **A pipeline copy only moves the tables its code names without a schema.** The copy publishes to the schema you pass, so a table named `orders` goes there, but one named in full, such as `prod.sales.orders`, is still written where it says. Read such names from the pipeline's configuration and set them with `lakeflow.pipeline(configuration=...)`. The copy runs the code the last `bundle deploy` uploaded, as you, in development mode, and leaves out the deployed pipeline's event log, so read its events with `PipelineUpdate.events()`. A pipeline that publishes to the Hive metastore, without a catalog, cannot be copied. `lakeflow.pipeline()` needs `sync="deploy"`.
- **A pipeline copy has no `parameters`.** `pipelines/get` returns no `parameters` for a pipeline, even one created with them, so a copy cannot carry the deployed pipeline's. Set what the code reads with `lakeflow.pipeline(configuration=...)`.
- **On databricks-sdk 0.100 to 0.109, a deleted pipeline copy keeps its tables.** `pipelines.delete` takes `cascade` from databricks-sdk 0.110.0, and without it Unity Catalog keeps the tables of a deleted pipeline until their schema is dropped. Publish copies to a `lakeflow.schema()`, which drops them with the schema, or upgrade databricks-sdk.
- **The pipeline update is found by time.** The Jobs API does not say which update a pipeline task started, so `TaskRun.pipeline_update` is the update of the pipeline created between the task's start and end, one started by a job task first. Two pipeline tasks that update the same pipeline in one run, or anyone else updating the deployed pipeline while the task runs, can make the match ambiguous. `events()` lists the pipeline's events newest first and stops at the first event logged before the task started, so it reads every event logged since then, those of later updates included, and keeps the update's own.
- **`setup=` and `teardown=` functions ship as source.** They run as notebooks on the job's compute, so they must be self-contained: imports inside the function, no helper functions defined elsewhere in the test module, no variables of an enclosing function. Lambdas, closures, decorated functions and functions defined in a REPL are refused with `LakeflowError`. `params` holds the parameters the platform passes to the task: declared ones and any passed undeclared under `allow_undeclared_params=True`, read with `dbutils.widgets.getAll()`; on a helper cluster older than Databricks Runtime 13.3 LTS, which has no `getAll`, only the declared ones and the keys of `job(params=...)` reach it. Each costs one extra task start per run, like a stub.
- **Stubbed outputs are literals.** A stub cannot run a query or evaluate an alert, so a `Stub`'s `outputs` replace the `{{tasks.<key>.output.<path>}}` references in the copy's settings with fixed strings. Give `rows` and `first_row` in the platform's format: on a SQL file task, `rows` resolves to a JSON array of row objects and `first_row` to one such object, written compactly, every value a string and `NULL` as an empty string, such as `{"n":"1","m":"","b":"true"}` (`TaskRun.sql_result` gives `None` for the same `NULL`). Code that reads the task's own output with `dbutils` instead of a reference in its settings is not affected.
- **Task values need probes.** Task values are not available through the Jobs API, so they are read by probe tasks. Each probe costs 7 to 30 seconds of serverless compute, even when its task did not run. For the same reason `lakeflow.task(..., upstream_from=run)` can only replay a task from a run that captured its upstream tasks' values with `capture_task_values`, never from a production run.
- **Concurrent sessions sharing one target.** Sessions that deploy the same target share one deployment, so a deploy from one session replaces the wheels that another session's jobs are still running, and those jobs fail. `deploy_flags=["--fail-on-active-runs"]` does not prevent this, because it only sees runs of the deployed jobs, not the ephemeral copies. Use the recipe in [isolating test deployments](how-it-works.md#isolating-test-deployments).
- **Job code must read catalog and schema from job parameters.** Bundle variables are fixed at deploy time, and the plugin deploys each target once per session for each set of `variables`.
- **Different setups of one target can collide under xdist.** `Lakeflow` instances for the same target that differ in `variables`, `sync` or `helpers_path` are set up separately, so two xdist workers can deploy that target at the same time and one of them can fail on the CLI's deployment lock. Give each set of variables its own target.
- **Serverless may run a cached wheel with the same file name.** A bundle wheel artifact without `dynamic_version: true` is uploaded under the same file name on every deploy while its version is unchanged. databricks/cli#1621 and databricks/cli#2958 report serverless compute running the cached old build in that case, so a test could pass or fail against code you have already changed. A probe in the maintainers' test workspace in October 2026 did not reproduce it: after the example wheel was rebuilt with changed code, the same version and the same environment `dependencies`, and redeployed, two serverless runs one minute apart both ran the new code. When the bundle summary (or, with `sync="sync"` or `"none"`, the validate output) lists such an artifact, an artifact of `type: whl` or one with a `build` command and no `type`, the first template lookup of the session emits one `UserWarning` (one per xdist worker): `Artifacts ['lakeflow_example'] have no dynamic_version: true. Serverless caches wheels by file name, so a rebuilt wheel with the same version may not be picked up. Set artifacts.<name>.dynamic_version: true in databricks.yml.` Set `dynamic_version: true` on the artifact, which makes the CLI add a unique local version to every build, or bump the version. `Lakeflow(strict_artifacts=True)` raises `LakeflowError` with the same text instead.
- **With `sync="none"`, a wheel built after the last deploy is caught by its modification time only.** The plugin warns when a local library file is newer than its uploaded copy by more than 60 seconds: `` dist/pkg-0.1-py3-none-any.whl was built after its uploaded copy. Run `databricks bundle deploy -t test`. ``, or raises `LakeflowError` with `strict_artifacts=True`. The 60 seconds allow for clock skew between the build machine and the workspace, so a rebuild within a minute of the deploy goes unnoticed, and a clock that is more than a minute fast warns about a wheel that was deployed. The comparison reads times, not contents: it misses a wheel deployed from another checkout, an older build copied over a newer one, and code changed but not rebuilt. It covers the local libraries of the bundle's jobs, not local paths in `extra_dependencies`.
- **`extra_dependencies` skips serverless notebook tasks without an environment, and wheel extras skip clusters.** A serverless notebook task without an `environment_key` cannot take dependencies from the job settings, so it is left unchanged, and named in a `UserWarning` when the job is created, as is every notebook task whose final compute does not list the packages: `` extra_dependencies ['faker==30.0.0'] do not reach tasks ['extract', 'transform', 'load'] of job 'my_example_job': neither the environment nor the cluster libraries of these notebook tasks list them, and a serverless notebook task without an environment_key has neither. Install them with %pip install in the notebook, or run the task on an environment that lists them. `` Install the packages with `%pip install` in the notebook, or move the task onto an environment that lists them, see [Test-only dependencies](job-tests.md#test-only-dependencies). A local wheel with extras such as `./dist/*.whl[test]` raises `LakeflowError` when the copy has a Python task on a cluster, because `libraries[].whl` takes no extras.
- **Single-task jobs keep only the target task.** On a shared job cluster a task can import libraries that other tasks declared, and on its own it loses them. Declare every library on the task that needs it.
- **Serverless auto-retry is off by default** in ephemeral jobs, for notebook, Python script, Python wheel and JAR tasks, so a test sees one attempt. Pass `disable_auto_optimization=False` to keep the platform's behaviour. To test retries, set `max_retries` on the task with [`task_overrides`](job-tests.md#retries-and-timeouts), which this setting does not affect. When a task is retried, `TaskRun` describes the last attempt and its `attempts` holds every attempt.
- **The Databricks CLI is required.** Deploying is only possible through the CLI, so the plugin shells out to it. There is no pure-SDK mode.
- **One run at a time per ephemeral job.** Each copy is created with `max_concurrent_runs: 1`. Parallelism comes from separate tests, each with its own job, or from several copies in one test, each started with [`start()`](job-tests.md#start-a-run-without-waiting) and waited for afterwards.
- **`sync` and `none` strategies read `bundle validate` output**, which leaves library paths local and `${resources...}` references unresolved. Jobs affected by that are refused, with an error that says to use `deploy`.
- **`single_node` needs dedicated access mode.** Single node compute does not support standard access mode, so `Lakeflow(single_node=True)` raises `LakeflowError` naming the first job cluster or task cluster whose `data_security_mode` is `USER_ISOLATION` or `DATA_SECURITY_MODE_STANDARD`. It sets the explicit single node fields (`num_workers`, `spark_conf` and the `ResourceClass` tag), not `kind` and `is_single_node`; the Clusters API accepted them as they are on a `SINGLE_USER` job cluster without a policy, and a cluster policy that forbids `spark.databricks.cluster.profile` would refuse them.
- **Standard (shared) access mode** classic clusters were not tested. There, task values set from wheel or script tasks may be silently lost.
- **Run Job tasks run the deployed child job.** The copy keeps `run_job_task.job_id` as deployed, so a test of a parent job starts a real run of the child, with the child's `run_as` and notifications, which is not cancelled or deleted with the ephemeral job. `lakeflow.job()` and `lakeflow.task()` warn about each such task that is not disabled, not downstream of a disabled task and not inside a disabled loop; `children="refuse"` raises `LakeflowError` instead, before anything is created. `TaskRun.child_run_id` gives the id of the child's run, and `TaskRun.child_run` gives the run as a `JobRun` with the child's tasks. Copying or stubbing the child is not supported yet.
- **Forced conditions apply to the whole copy.** `force_conditions` rewrites the copy's settings, so every run of that copy takes the same branch; make another copy, for example in a parametrised test, for the other branch. The condition task keeps its `depends_on`, so the tasks upstream of it still run. If `disable` disables one of them, the platform disables the condition task and both branches as well, because they are downstream of a disabled task, so forcing that condition task raises `LakeflowError` before the job is created. Without `force_conditions`, the plugin lists the condition task and both branches in `run.disabled_tasks` with the tasks named in `disable`. When that leaves no task enabled, the platform skips the whole run ("Skipped because every task is disabled") and no task gets a result state: the plugin lists every task in `run.disabled_tasks` with `ran` false, `run.succeeded` is false, and `repr(run)` names the platform's reason as `run: <message>`. Condition tasks nested in a `for_each_task` cannot be forced.
- **For-each tasks have limits of their own.** `run.task("loop").iterations` holds one `TaskRun` per iteration, read with one `get_run_output` and one `get_run` for each attempt of each iteration, so a long loop makes the result slower to build. An iteration's input is not reported on its own: it shows in the iteration's `parameters` only where the nested task passes `{{input}}`. An iteration cannot set task values (the platform refuses `taskValues.set()` there), so `capture_task_values` on a for-each task captures nothing. Iterations are not exported to `notebook`. The task nested in a for-each task cannot be the target of `run(only=...)`. [`lakeflow.task("job_key.loop_key.nested_key", input=...)`](task-tests.md#for-each-bodies) runs the nested task once, without its loop. [`for_each_inputs`](job-tests.md#for-each-tasks) shortens the list the copy iterates over, but only for a top-level for-each task, and only as a literal list of at most 5,000 characters as JSON, of all primitives or all objects.
- **A lifted for-each body sees its input as job parameters.** Only the `{{input}}` and `{{input.<key>}}` references in the body's settings are rewritten, to `__pytest_input` job parameters, which a notebook also gets as widgets. The plugin writes an object input as a for-each iteration in the workspace did, compact with every number as a double (`{"id":7.0,"path":"/x"}`), but keeps your key order, which the platform does not keep for larger objects. A body run outside its loop may set task values, which an iteration cannot.
- **Only trigger references in the settings can be simulated.** [`trigger`](job-tests.md#simulate-a-trigger) rewrites the `{{job.trigger.<path>}}` references in the copy's settings, so code that reads the trigger context another way still sees a run-now run, and `run.trigger_type` stays `ONE_TIME`. A reference that `modify_settings` adds is not rewritten. A list value, such as the tables of `table_update.updated_tables`, is passed as the string the test gives, because the format the platform uses for it has not been recorded on a triggered run yet. A job whose tasks or job parameter defaults use `table_update` or `file_arrival` references cannot be copied without `trigger` setting them, because the copy has no trigger and `jobs/create` refuses them, so the plugin raises `LakeflowError` naming the task or job parameter and the reference when the job is created. The values are fixed for the copy, so every run of it sees the same ones.
- **Debug notebooks replay parameters only.** A notebook from [`debug_notebook()`](job-tests.md#reproduce-a-failed-notebook-task) sets the task's resolved parameters as widgets and runs the task's notebook with `%run`; it does not restore task values or the Spark session. A task that calls `dbutils.jobs.taskValues.get()` without `debugValue=` raises `TypeError` in it, and a text widget holds at most 2048 bytes, so a longer value reaches the notebook truncated; the notebook and the terminal summary name those parameters. On serverless environment 5 or later, when you are the run's run-as user, Databricks' own Session restore ("Debug in new notebook" on the run page) restores the session itself. Notebook tasks inside a `for_each_task` are not covered.
- **Names starting with `__pytest_`** are reserved for the plugin's tasks, environments, widgets and parameters, such as the `__pytest_test_id` job parameter that `test_marker=True` declares. Tests cannot pass them as `params` or as parameter names in `task_params`.

## FAQ

### Why deploy the bundle instead of reading `databricks bundle validate`?

`validate` resolves notebook paths but leaves wheel and JAR paths pointing at local files, and does not resolve `${resources...}` references. A deploy builds and uploads the wheels and gives job settings in which every path is a workspace path, read back with `jobs.get`. The deploy happens once per session, and a deploy of an unchanged bundle takes seconds. If you deploy the target yourself, `Lakeflow(sync="none")` skips it, see [sync strategies](configuration.md#sync-strategies).

### Why not rely on `bundle validate`?

Checking a bundle's schema and types is the CLI's job, and `bundle validate` does it. It does not model the Jobs API's own rules, so it passes a `{{job.parameters.<name>}}` the job does not declare, a `{{tasks.<key>.values.<name>}}` whose task is not upstream, a `depends_on` task that is not in the job and retries on a `for_each_task`, and the deploy refuses most of them later, one at a time. `lakeflow.check(key)` checks those Jobs API rules on the template without creating anything, see [Check a job without running it](job-tests.md#check-a-job-without-running-it).

What `bundle validate` reports of each rule of `lakeflow.check`, checked against the CLI version the plugin requires at least and checked again each time that minimum is raised. A rule is dropped once the CLI reports what it does.

| Rule | `bundle validate` | CLI version checked |
|---|---|---|
| Undeclared `{{job.parameters.<name>}}` (always applied) | Passes it | 1.7.0 |
| `{{tasks.<key>.values.<name>}}` whose task is not upstream (always applied) | Passes it | 1.7.0 |
| `depends_on` task that is not in the job (always applied) | Passes it | 1.7.0 |
| Retries on a `for_each_task` (always applied) | Passes it | 1.7.0 |
| `wheel`: entry point missing from the built wheel | Passes it | 1.7.0 |
| `library`: absolute library, Python file or environment dependency path that does not exist | Passes it | 1.7.0 |
| `dash`: task reference to a task key with a dash | Passes it | 1.7.0 |
| `trigger`: `{{job.trigger.*}}` reference | Passes it | 1.7.0 |
| `equal_to`: `EQUAL_TO` or `NOT_EQUAL` on a number or a task value | Passes it | 1.7.0 |

### Why do my tests never run the deployed job?

The deployed job keeps its schedule, notifications, `run_as` and bundle lock, and running it would mix test runs with real ones. Each test instead gets a copy with those removed and its dashboard and SQL alert subscriptions paused, named and tagged after the test, so runs are isolated and attributable and do not email subscribers. Alert and Power BI tasks are left alone; see [Limitations](#limitations). Jobs are cheap to create and delete.

The copy runs as you rather than as the deployed job's `run_as`. To exercise the permissions of that principal, opt in with `lakeflow.job(key, run_as="keep")`, see [Run as another identity](job-tests.md#run-as-another-identity).

### Why is my job parameter rejected?

The Jobs API accepts undeclared parameters silently, so a typo would pass unnoticed. The plugin checks `params` against the job's declared `parameters` and raises `LakeflowError` for anything undeclared. Declare the parameter on the job, or pass `allow_undeclared_params=True`.

### Why is every run 3 to 4 minutes slower than in the UI?

The job's `performance_target` is `STANDARD`. The plugin warns about it. Pass `performance_optimized=True` to run tests with `PERFORMANCE_OPTIMIZED`, or `job.run(performance_target="PERFORMANCE_OPTIMIZED")` to speed up one run without changing the job's settings. `run.effective_performance_target` and each task's `effective_performance_target` show which mode the run actually used.

The other cause is a workspace that does not honour the request. When a run asked for `PERFORMANCE_OPTIMIZED`, through `performance_optimized=True`, `run(performance_target=...)` or the template, and `run.effective_performance_target` is `STANDARD`, a workspace policy or the job's compute decided the mode, and the plugin warns once per `Lakeflow`:

```text
UserWarning: Run 123 of 'my_job' asked for PERFORMANCE_OPTIMIZED but used STANDARD. A workspace policy or the
job's compute decides the performance mode; expect 3 to 4 minutes extra per run.
```

Nothing in the test can change that; ask a workspace admin about the policy.

### How do I clean up after a crashed session?

Ephemeral jobs are tagged `pytest` and `pytest_run_id`, and, when they can be found out, `pytest_ci_url`, `pytest_user`, `pytest_git_sha` and `pytest_git_branch`, so a leftover job can be traced to its CI run, person and commit from the Jobs list. `pytest --lakeflow-sweep` deletes your own jobs and pipeline copies from other runs that are older than `sweep_hours`, 24 hours by default. Add `--lakeflow-sweep-schemas=<catalog>` to drop the temporary schemas of crashed sessions too, `--lakeflow-sweep-notebooks` for old `setup_<hash>` and `teardown_<hash>` notebooks, and `--lakeflow-sweep-scope=all` to clean up after everyone, which needs the right to delete their jobs and schemas. Run it with `--lakeflow-sweep-dry-run` first to see what it would delete. A job or schema made under `--lakeflow-keep-ttl` is kept until its `pytest_expires` time, and so are the setup, teardown and debug notebooks of every job the sweep keeps. `Lakeflow(...).sweep()` runs the same sweep from a script, without a test or a bundle deploy. See [sweeping leftovers](configuration.md#sweeping-leftovers). `pytest --lakeflow-destroy` runs `bundle destroy` for the test target at the end of the session.

### What does the plugin leave in my workspace?

The deployed test target, the two helper notebooks under `helpers_path` with the `setup_<hash>` and `teardown_<hash>` notebooks of any `setup=` and `teardown=` functions, and any jobs and pipeline copies kept by the keep rules. A kept job's tags (`pytest_run_id`, `pytest_nodeid`, `pytest_job_key`, `pytest_ci_url`, `pytest_user`, `pytest_git_sha`, `pytest_git_branch`) and description say which test, run, person and commit made it. See [How it works](how-it-works.md#what-is-left-in-the-workspace).

### Why does setup fail with "Bundle target 'test' deploys to ... but the workspace client is for ..."?

The CLI and the SDK resolved different workspaces. The CLI takes the host from the target's `workspace.host` in `databricks.yml`, while the plugin's `WorkspaceClient` takes it from `profile` or the `DATABRICKS_*` variables. Without this check, every `jobs.get` would look in the wrong workspace and the jobs would be reported as stale. Make the two agree: pass `profile=` to `Lakeflow` for a profile whose host is the target's, set `DATABRICKS_HOST` and `DATABRICKS_CONFIG_PROFILE` to match the target, or run pytest through the CLI with `databricks bundle run -t test -- uv run pytest`, which gives it the target's credentials. A target without `workspace.host` is not checked.

### Why does setup fail with "Target 'test' sets run_as ..."?

Before `bundle deploy`, the plugin reads the `run_as` of the target and of each job from `bundle validate` and compares it with the identity that deploys. A deploy with another user's `run_as`, or a service principal on which you do not have the Service Principal User role, would either fail inside the CLI after a long deploy or leave jobs that run as someone else. Set the test target's `run_as` to `user_name: ${workspace.current_user.userName}`, so that each identity deploys jobs that run as itself, deploy as that principal, for example from CI, or ask a manager of the service principal to grant you the role. To keep a `run_as` you cannot deploy, deploy the bundle yourself as the right identity and pass `sync="none"` to `Lakeflow`. Giving each identity its own deployment is described in [Isolating test deployments](how-it-works.md#isolating-test-deployments).

### Why did the CLI fail with `exit status 45` under xdist?

Each xdist worker builds its own `WorkspaceClient`. On a user-to-machine profile (`auth_type = databricks-cli`, from `databricks auth login`), databricks-sdk runs `databricks auth token --force-refresh` to get the token, so every worker refreshes the same cached token at the start of the session. When two refreshes update the CLI's token cache at the same moment, one of them fails with `cannot get access token: Error: forced token refresh: cache update: exit status 45`. The plugin tries to build the client up to four times. Before each of the three retries it logs `Retrying workspace client after: ...` at INFO and waits a random time (2 to 4 seconds, then 4 to 8, then 8 to 16), so that workers that collided do not collide again. A test still fails if every attempt collides.

If you still see it, run with fewer workers, or use a profile that does not refresh through the CLI for parallel runs: a service principal with OAuth machine-to-machine credentials (`client_id` and `client_secret`) or a personal access token (`token`). For example, keep the `databricks-cli` profile `dev` for everyday runs and choose a machine-to-machine profile `dev-sp` for parallel runs through an environment variable:

```python
import os

import pytest

from pytest_databricks_lakeflow import Lakeflow


@pytest.fixture(scope="session")
def lakeflow() -> Lakeflow:
    return Lakeflow(target="test", profile=os.environ.get("LAKEFLOW_PROFILE", "dev"))
```

```bash
LAKEFLOW_PROFILE=dev-sp uv run pytest tests -n 4
```

### Does it work alongside databricks-labs-pytester?

Yes. The plugin defines only the `lakeflow` fixture and does not import pytester, so the two can be installed together. `lakeflow.ws` gives you the `WorkspaceClient` without a second fixture.

### How does `lakeflow.pipeline()` differ from pytester's `make_pipeline`?

pytester's `make_pipeline` builds a new pipeline from the keyword arguments you give it, by default with a random name, a generated notebook and a classic cluster, and deletes it afterwards. `lakeflow.pipeline()` copies a pipeline your bundle deployed, from its deployed spec, so the copy runs your pipeline's own code on its own compute, and redirects it into the schema you pass. `pipelines="copy"` on `lakeflow.job()` goes one step further and points a job's pipeline tasks at such copies, which pytester has no equivalent for. Use `make_pipeline` for a pipeline that exists only for the test, and `lakeflow.pipeline()` to test the one in your bundle.

### Can I use `Lakeflow` outside pytest?

No. It raises `LakeflowError` outside a pytest session, and outside a test. Jobs are tied to the running test for naming, tagging and teardown. `lakeflow.attach(run_id)`, which reads a kept job's run back without running it, also runs inside a test, which records the run in its report section.

### How do I see what is happening?

Run with `--lakeflow-live` to print each task's change of state to the terminal while a run is in flight, with the run's URL, and nothing from other loggers; `job.run(stream=True)` does the same for one run. Under xdist the workers cannot print to the terminal, so use the report section there. Run with `--log-cli-level=INFO` for the deploy, create, run and delete lines with their URLs, and a line for each task's change of state while a run is in flight, such as `transform: RUNNING -> FAILED in 0:00:42 ValueError: no rows`. The URLs, followed by the task lines, are in the `lakeflow` section of each test report (for setup and teardown errors as well as failures, and for passing tests with `-rA`), and in JUnit XML as the `lakeflow_job_url`, `lakeflow_run_url` and, for a pipeline copy, `lakeflow_pipeline_url` properties, beside `lakeflow_job_id`, `lakeflow_pipeline_id`, `lakeflow_run_id`, `lakeflow_result_state`, `lakeflow_duration` and, for a failed run, `lakeflow_failing`, `lakeflow_params` and `lakeflow_task_params`. At the end of the run, a `lakeflow` block in the terminal summary lists the kept jobs, pipeline copies and schemas and the runs cancelled at session end. See [logging and reports](configuration.md#logging-and-reports).

### Which clouds and runtimes are supported?

The plugin uses only the Jobs API, the Pipelines API, the Workspace API, the Unity Catalog schemas API and the CLI, which are the same on AWS, Azure and GCP. It was developed and tested against an Azure workspace with serverless jobs and classic job clusters in dedicated access mode.
